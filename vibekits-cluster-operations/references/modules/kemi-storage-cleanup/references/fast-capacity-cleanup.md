# 大缓存区与30秒快速执行

用户要求清到300 GB、指出数百GB构建缓存未清，或要求30秒完成时读取。容量目标、最新时限、已有授权和数据保护仍按主技能执行；本文件改善发现与执行速度，不增加删除源码、SDK、当前任务输入或未知内容的权限。

## 先用有效索引直接执行，避免再次从小旧清单起步

1. 读取最近一轮的卷基线、一级空间盘点、生成目录位置索引、逐文件生成依据及未完成回执。先取实际可用字节，固定本轮是“剩余达到N GB”还是“净释放N GB”。本机300 GB案例沿用外盘可用300,000,000,000字节目标。
2. 更新当前任务的精确路径、安装/交付版本、发布渠道和平台、进程及必要恢复输入。保留具体源目录/目标目录，不能因为一个子目录在用就排除整个父级。例如`resources-dev523-20261005/source648`与同父级的闲置旧快照必须分别判断。
3. 索引里仍有效的旧生成物先执行：复核规范路径、设备/inode/大小/mtime、源输入及当前引用，分批检查打开文件。按预计可回收的大对象优先，实际回读容量后决定下一批，不重复索取同范围授权。
4. 记录开始和30秒检查点的实际可用字节、已删对象及目标状态。30秒未达标就标为未达，继续同范围补扫和清理，不把快速阶段结束当成任务完成，也不把文件分配大小相加当作释放容量。

“30秒清到300 GB”必须以当次完整实测通过为准；没有足量可删对象、首次冷盘扫描、完整SHA校验、文件系统延迟或并发写入时，不能将历史成功或预先准备清单写成保证。下一次的速度改进来自保留和更新有效索引，而不是跳过核验。

## 索引不足时覆盖整个缓存区，补齐真正的生成位置

- 一次完成一级目录盘点，持续写入有界进度；最大分组深入，超时单列未知，不写0。不要对同一子树同时运行父级和子级全量du；不要重复扫描已经完成的原始输入树。
- 用目录标记发现源码位置：`pubspec.yaml`、Cargo目标中的`.fingerprint`及相应depfile。发现位置不等于可删清单；第三方包和源码快照不能计成独立项目数量。
- Flutter不能只看`build`：另查`.dart_tool/flutter_build`、`.dart_tool/hooks_runner`、`.dart_tool/pub/bin`、`.dart_tool/build/entrypoint`中的已核实生成内核、汇编、对象。原生资产、JNI staging及冻结依赖元数据继续保护。
- Rust不能只沿用旧的14个target：重新发现目标profile和增量目录，核实rlib/rmeta的格式、匹配depfile与实际保留crate；增量bin验证RSIC和对应源码。当前target和服务目录排除。
- Gradle区分生成API JAR、transforms、Kotlin DSL类与原始modules-2、wrapper、分发工具。生成JAR核验内容，转换物定位保留原件。
- CMake补扫不能只查vcpkg：沿已发现的Android `.cxx`、Rust `OUT_DIR`及其他原生生成位置读取真实`CMakeCache.txt`，核对`CMAKE_HOME_DIRECTORY`对应的保留源码和`CMakeLists.txt`。对象文件还须位于实际`CMakeFiles`、验证ELF/Mach-O格式及逐文件时限；安装好的SDK库不随构建树清除。
- 对SDK重复副本可沿用已验证的APFS同字节共享块：完整SHA256与元数据校验、同设备、无占用/未知ACL/符号链接；路径、字节、权限、owner、纳秒时间和xattrs保留。SDK输入不删除，当前工作区不修改。复制、共享块及实际可用净增分别记录。

包和符号按实际身份、平台与渠道的当前交付核验，不按全产品最大数字推断所有旧包可删。例如本机KOffice归档10137不能因“137/127”文字比较判过期；VibeKits当前Developer ID版本与保留Store2226也要分别记录。未解除的金丝雀/恢复拒绝范围仍保留。

## 批次和接续必须修正的两个细节

- 冻结前对精确路径去重，保留源/目标别名关系。删除前先剔除并记录已消失对象，再对存在的对象执行lsof；否则一个不存在路径的stderr会让整批被误记成打开检查错误。错误类型与stderr摘要单独保存，不能把原候选说明当作跳过原因。
- 使用增量回执或适度检查点，避免每删一个小文件就重写全部清单。新出现的同路径对象比较原inode/大小/纳秒mtime，新生成对象保留。断线先对账回执，不重复未知结果的操作。
- 同一卷只有一个变更队列。工具返回运行中的session/cell ID只是已启动，必须等该批完成并回读后再启动下一批删除或共享块替换；不能把已await启动误当作已完成。
- SDK副本的保护范围要上溯到实际项目：SDK子目录未出现在命令行，不等于其所属项目闲置。用最近的项目配置定位owner，排除当前任务引用或运行进程指向的owner；同字节替换前除inode/大小/mtime外还核对ctime，避免覆盖并发改写后恢复mtime的对象。清单裁剪后，接续条件用“现有候选路径减已处理路径”，不能只比较两个数量。
- 位置索引同时登记当前、未满两天和待核目录及其发现父目录的身份/子项快照；它们不进入删除清单，但后续不能漏掉。下次先检查父目录新子项及已变更位置，补新生成目录并重新判断时限，不能永远只查首次盘点时已满两天的旧路径。

### 历史工作区中的深层Gradle生成缓存

下次用户要求“按本次方法继续清理”时，按以下顺序复用；本节不是静态删除白名单。

1. 读取最近的summary、目录位置索引、manifest/result/journal和未完成事务，记录本次卷可用字节、容量目标、时间范围与仍有效授权。更新各平台/发布渠道的最新构建、当前正式包、精确任务引用及进程占用；父子目录不重复计量，不因一个子项在用而保护整个历史分组。
2. 从已有Gradle home列表、缓存父目录和文件索引补出深层生成位置，覆盖中心缓存区与其他已授权项目目录；同时检查旧App包、旧安装验证副本及镜像。索引只用于发现，Spotlight漏收录或旧查询为空不能证明整组没有输出。
3. 核实生成来源和保留输入，冻结新清单，记录规范路径、device/inode/size/mtime、分配占用、类别、保留依据和清理理由。依赖目录若为空须注明；先定位真实依赖原件或保留的构建配置及重建路径，不能把空目录当作输入保全证据。当前步骤的原生资产、有效stamp及实际恢复依赖继续保护。
4. 对精确文件分批检查lsof和进程，按原对象身份复核后删除，同一卷保持一个变更队列；等待该批完成并读取回执再启动下一批。消失、变更、占用及检查失败分别记录，不追删同路径新对象。每批复测空间，达到当次容量目标停止新增删除。
5. 对已执行清单回读原对象是否消失，再在已核实生成单元内移除空目录。交付文件数、空目录数、分配占用和实际可用净增，说明剩余差额及待核目录；删除完成、源码同步完成、整工作区移除与容量达标分别验收。
