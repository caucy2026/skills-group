# 服务更新未生效：先验证观察方法（2026-10-03）

这是 hbbv 原服务上的实测经验，不是所有服务通用的启动耗时保证。

两次候选重载在约30秒观察后回滚。保持旧版代码、原数据库和原 supervisor 作对照，旧版的新PID约1秒出现，HTTPS却约31秒才恢复；候选按原流程重载并采用有界100秒观察后同样约31秒恢复。实际加载源码哈希、MCP已加载标志、原服务UUID和经认证目录均通过。不能因此归因于新版代码，也不能把启动延迟本身宣称已经查明。

可复用步骤：

1. 先从实际 supervisor 的运行配置获取命令、环境、stdout/stderr路径和当前PID；不要检查猜测的空日志文件。
2. 网络工具的 PermissionError、观察超时和进程终态分别记录。沙箱限制不证明服务故障；按平台审批使用授权的同范围只读探测，不关闭TLS。
3. 保留首败、候选和回滚哈希。确认没有执行中任务，再使用原正常停止/自动恢复路线，先验证旧版恢复行为；不同时改源码、启动方式和配置。
4. 启动时可增加无凭据的实际模块路径、源码SHA和已加载功能标志。新PID存在不表示服务ready；文件已写入也不证明运行进程加载了该文件。
5. 观察窗口依据实际旧版恢复证据设置，仍须有上限。请求失败时跟踪同一真实PID和日志，不因一次短超时反复重启或回滚。
6. 成功须同时满足原服务身份、实际加载候选、HTTPS与认证功能。随后复核原设备房间心跳及版本；不重置数据库、设备身份、密钥或授权。

本次已签App的真实Node/MCP SDK经stdio管理适配器读到原房间、原Office任务和审计事件。仅证明管理通道可用；App组长会话配置、自主发布/领取/执行、五机升级和独立验收仍未完成。原任务仍为竞标状态。

设备ID以原合同和实时目录为准；不能把机器标签与数字ID拼接。管理快照的readyCount不包含运行签名、授权延续、模型回复和任务执行。

项目证据：hbbv docs/acceptance/MANAGEMENT_MCP_2026-10-03.md；外盘验收目录中的 baseline-supervisor-reload-diagnostic.json、provenance-gated-live-deployment.json 和 live-sdk-readonly/stdout.json。新任务重新核验现场，不照搬本机绝对路径或PID。
